1. EXECUTIVE OVERVIEW & PROBLEM STATEMENT
--------------------------------------------------------------------------------
India's rapid gig economy powers urban logistics through millions of platform
workers (Zomato, Swiggy, Zepto, Blinkit, Rapido, Uber, Porter). These workers
regularly operate in grueling 10–14 hour shifts under extreme weather (38°C–44°C).

The core operational vulnerabilities they face include:
- Denial of Restroom Access: Commercial complexes and upscale restaurants routinely
  prohibit delivery partners and cab drivers from using their sanitation facilities.
- Unreliable Drinking Water: Public dispensers are frequently broken, dry, or locked
  behind gated commercial compounds.
- EV & Device Charging Anxiety: Delivery smartphones run high-drain GPS navigation
  continuously, and EV scooter riders face sudden battery exhaustion along corridors.
- Heatstroke, Fatigue & Accident Risk: High-pressure platform delivery algorithms
  incentivize non-stop delivery runs, resulting in dehydration and fatigue-induced
  road accidents.

RESTORA is a civic-tech urban infrastructure platform that solves these problems
by discovering, verifying, routing to, and evaluating safe urban rest stops with clean
washrooms, free drinking water, phone/EV charging, shade, and parking.

2. SYSTEM ARCHITECTURE & TECH STACK
--------------------------------------------------------------------------------
The project is built as a production-grade full-stack web application:

FRONTEND:
- Framework: React 19 (TypeScript)
- Build Tool: Vite 8
- Mapping: Leaflet 1.9 + React-Leaflet 5 (OpenStreetMap tile layers, zero paid API keys)
- Styling: Custom Vanilla CSS design system with responsive layouts & modern tokens
- Icons: Lucide-React
- Geolocation: Native Browser Geolocation API (getCurrentPosition + watchPosition)
  with a 35-meter displacement threshold to prevent GPS jitter and API spam.
- State Management: React Context (AuthContext) and state hooks.

BACKEND:
- Framework: Python 3.11+ FastAPI (Asynchronous REST API)
- Persistence: SQLAlchemy 2.0 ORM
- Database Options:
  * Primary: Supabase PostgreSQL (via transaction pooler port 6543)
  * Fallback: Local SQLite database (restora.db) with automatic fallback
- Security: PBKDF2-SHA256 password hashing, HS256 JWT Bearer token authentication
- Mathematical Services:
  * Haversine Great-Circle distance calculation in meters
  * Corridor Vector Projection for detour calculation along delivery routes
  * Multi-factor explainable recommendation scoring engine

DEV RUNNERS & SCRIPTS:
- `dev_all.py` / `npm run dev:all`: Concurrent runner launching FastAPI (port 8000)
  and Vite dev server (port 5173 with HMR).
- `run_dev.py` / `npm run dev:backend`: Backend only.
- `check_db.py`: Diagnostic connectivity script testing Supabase PostgreSQL / SQLite.
- `verify_fullstack.py`: End-to-end automated verification script testing APIs and HTML.
- `backend/tests/test_api.py`: Automated pytest test suite covering all 7 modules.

3. THE 7 CORE FUNCTIONAL MODULES
--------------------------------------------------------------------------------

MODULE A — WORKER AUTHENTICATION & PROFILE:
- JWT Bearer token authentication with role-based access control (`worker` vs `admin`).
- Profile fields tailored to field gig work:
  * Name, email, phone number.
  * Worker Category: delivery_rider, cab_driver, courier_worker, logistics_worker, other.
  * Preferred Language: en (English), ta (Tamil), hi (Hindi), te (Telugu), ml (Malayalam).
  * Work Area: Primary corridor (e.g. "Peelamedu, Coimbatore").
  * Hourly Rate Estimate (INR): Used exclusively for personal voluntary downtime estimates.
- Guest Mode: Complete map viewing, locality search, and nearby discovery work
  without requiring login. Login is only required for contributing verifications,
  incident reports, or saving bookmarks.

MODULE B — REST-POINT DISCOVERY & ADAPTIVE MAP:
- Interactive Leaflet map with custom emoji pins:
  * Rest / Seating: 🌳 (Indigo)
  * Washroom: 🚻 (Emerald)
  * Drinking Water: 💧 (Blue)
  * Phone/EV Charging: 🔋 (Amber)
  * Subsidized Food: 🍱 (Red)
  * Petrol Pump: ⛽ (Slate)
- Distinguishes Live GPS User Marker (pulsing blue) from Searched Locality Marker
  (amber pinpoint) so manual searches are never falsely claimed as live GPS.
- Adaptive Search Radius Engine: If fewer than 5 facilities are found within the
  initial 5 km radius, the search radius automatically increments by 1 km steps up
  to 20 km to discover the nearest verified oasis.
- Multi-criteria filter chips: Washroom, Drinking Water, Rest Seating, Charging, Food, Petrol Pump.

MODULE C — EXPLAINABLE INTELLIGENT REST RECOMMENDATIONS:
- Deterministic 100-point composite scoring algorithm:
  1. Proximity Score (0 to 40 pts): Linear decay from 40 pts at 0m to 0 pts at max_distance.
  2. Amenity Coverage Score (0 to 35 pts): Ratio of worker's selected needs matched.
  3. Operational & Access Status (0 to 15 pts): Open (+8 pts), Public Access (+7 pts).
  4. Verification Freshness (0 to 10 pts): Verified status (+5 pts), report in last 24h (+5 pts).
- Algorithmic Honesty: Every recommendation returns an explicit human-readable
  explanation string (e.g. "Recommended (95.3/100) because it is 353m away, matches
  your requested Water and Washroom, and has verified status"). No black-box AI scores.

MODULE D — REST-AWARE CORRIDOR ROUTE PLANNING:
- Designed for riders traveling between a pickup and a delivery dropoff.
- Geometry & Vector Mathematics:
  * Projects each rest facility onto the straight-line segment connecting Origin (x1, y1)
    and Destination (x2, y2).
  * Calculates the closest point on the corridor segment and computes the perpendicular
    detour distance (d_detour) using the Haversine formula.
  * Filters facilities within worker's customizable detour tolerance (0.5 km to 3.0 km).
  * Sorts candidate stops by lowest detour kilometers.
  * Explicit disclaimer: Informs workers that detours are geometric approximations
    and actual travel time may vary with one-way streets and traffic signals.

MODULE E — CROWDSOURCED INCIDENT REPORTING & MODERATION:
- Workers can flag facility conditions in under 10 seconds:
  * Issue Types: WATER_OUT_OF_ORDER, WASHROOM_DIRTY_LOCKED, CHARGING_NOT_WORKING,
    FACILITY_CLOSED, ACCESS_DENIED, SAFETY_CONCERN, INCORRECT_HOURS, OTHER.
  * Description & optional photo proof URL.
- Moderation Workflow:
  * Reports enter a `PENDING` queue.
  * Admins review and mark `APPROVED`, `REJECTED`, or `FLAGGED` with moderator notes.
  * Approving an issue report automatically updates facility status to `RECENTLY_REPORTED`.
- One-Click Verification: Workers on site can click "Verify Now" to confirm all
  amenities are functioning, incrementing the verification count.

MODULE F — VOLUNTARY BREAK PLANNER & INCOME IMPACT ESTIMATOR:
- Voluntary Rest Break Session Tracker:
  * Workers can start 10, 15, 20, 30, or 45-minute rest pauses with an active timer.
  * One-tap completion logs actual vs. planned duration.
- Illustrative Opportunity Cost Estimator:
  * Formula: Opportunity Cost = (Hourly Rate / 60) * Break Duration.
  * Ethical Safeguards: Explicitly discloses that rest pauses are personal health
    choices. Restora NEVER transmits break durations to platform algorithms or
    penalizes workers. Taking shade breaks prevents heatstroke and reduces crash risk.

MODULE G — ADMIN DASHBOARD & URBAN SERVICE GAP ANALYTICS:
- Platform Overview: Total rest points, verified count, pending reports, break sessions,
  registered workers.
- Facility CRUD: Add new verified points, edit metadata, or decommission facilities.
- Crowdsourced Report Moderation Queue with reviewer audit notes.
- Urban Service Gap Analytics: Visualizes high-density zones missing clean washrooms,
  canopy shade, or EV charging infrastructure to advocate for civic improvements.

4. DATABASE SCHEMA & ENTITY DEFINITIONS
--------------------------------------------------------------------------------

Table: `users`

- name (VarChar 120, NOT NULL)
- email (VarChar 150, UNIQUE, NOT NULL)

5. REST API SPECIFICATION
--------------------------------------------------------------------------------

Authentication & Worker Profile:
- `POST /api/auth/register` -> Creates user, returns JWT `{ access_token, token_type, user }`
- `POST /api/auth/login` -> Authenticates email & password, returns JWT
- `GET /api/auth/me` -> Retrieves authenticated worker profile
- `PATCH /api/auth/profile` -> Updates profile attributes (preferred_language, work_area, rate)

Facilities Discovery:
- `GET /api/facilities/nearby?lat={lat}&lng={lng}&category={cat}&service={svc}&initialRadius=5&step=1&minResults=5&maxRadius=20`
  -> Adaptive radius search returning `{ facilities, searchRadiusKm, expanded, message }`
- `GET /api/facilities?lat={lat}&lng={lng}&category={cat}&service={svc}&access_type={acc}&q={q}`
  -> Returns list of facilities sorted by distance
- `GET /api/facilities/{id}?lat={lat}&lng={lng}` -> Detailed facility view
- `POST /api/facilities` -> Create facility (Admin/Worker authenticated)
- `PATCH /api/facilities/{id}` -> Update facility
- `DELETE /api/facilities/{id}` -> Delete facility (Admin only)
- `POST /api/facilities/verify` -> One-click amenity verification

Intelligent Recommendations & Routing:
- `POST /api/recommendations/intelligent`
  Body: `{ lat, lng, need_water, need_washroom, need_charging, need_rest, need_shade, max_distance_meters }`
  Returns: `{ total_found, recommendations: [{ facility, score, explanation }] }`
- `POST /api/routes/plan`
  Body: `{ origin_name, origin_lat, origin_lng, destination_name, destination_lat, destination_lng, required_services, max_detour_km }`
  Returns: `{ origin, destination, total_route_distance_km, facilities: [{ facility, straight_line_dist_km, estimated_corridor_detour_km, stop_recommendation_reason }] }`

Crowdsourced Reports:
- `POST /api/reports` -> Submit issue report `{ facility_id, report_type, description, image_url }`
- `GET /api/reports?facility_id={id}&status={status}` -> List reports
- `POST /api/reports/{id}/moderate` -> Admin moderation `{ status: "APPROVED"|"REJECTED"|"FLAGGED", review_notes }`

Break Sessions & Bookmarks:
- `POST /api/breaks` -> Start break session `{ facility_id, planned_duration_minutes, notes }`
- `GET /api/breaks` -> List worker break sessions
- `PATCH /api/breaks/{id}` -> Complete break session `{ status: "COMPLETED", actual_duration_minutes }`
- `POST /api/breaks/estimate-impact` -> `{ hourly_rate_estimate, planned_break_minutes }` -> Returns opportunity amount & health disclaimer
- `POST /api/bookmarks/{facility_id}` -> Toggle bookmark
- `GET /api/bookmarks?lat={lat}&lng={lng}` -> List bookmarked facilities

Support Resources & Admin Overview:
- `GET /api/support-resources?category={cat}` -> Welfare boards, emergency numbers, clinics
- `GET /api/partner-offers` -> Worker beverage/meal subsidies & charging discounts
- `GET /api/admin/overview` -> Platform metrics & service gap analytics
- `GET /api/status` -> System health and active module status

7. AGENT ROLES & STRICT COLLABORATION BOUNDARIES
--------------------------------------------------------------------------------
This project is developed under a strict 3-agent division of labor:

AGENT 1 (AswinNS-dev / Maps & Facility Discovery):
- OWNERSHIP: Map component (`InteractiveMap.tsx`), location hook (`useLocation.ts`),
  nearby facility discovery UI, facility cards/modals, geocode service, Explore page.
- BOUNDARIES: Must NOT modify database schemas, migrations, backend models, auth
  providers, or the RakshitArtha income protection page.

AGENT 2 (Authentication & Income Protection):
- OWNERSHIP: Auth provider, login/signup flows, session management, and the
  dedicated RakshitArtha income-protection feature.

AGENT 3 (Database & Infrastructure):
- OWNERSHIP: Database schemas, SQL migrations, ORM tables, Supabase configurations.
